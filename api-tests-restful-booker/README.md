# Restful-booker API tests

Автотесты для учебного REST API бронирований [Restful-booker](https://restful-booker.herokuapp.com/apidoc/index.html).

Стек: Python, pytest, requests, pydantic

## Что реализовано

- API-клиент на классах (`Reservation`) с авторизацией по токену и `requests.Session`: CRUD бронирований.
- Тесты создания, получения, обновления (PUT / PATCH), удаления и авторизации.
- Позитивные и негативные сценарии: неверные типы данных, невалидные значения, пропущенные обязательные поля, несуществующие id, доступ без токена.
- Проверки статус-кодов и значений; для успешного создания и получения брони дополнительно проверяются структура и строгие типы через pydantic-модели.
- Клиент передаётся в тесты через фикстуры pytest, негативные кейсы параметризованы.
- Тестовые брони удаляются автоматически после каждого теста.
- Проверки предполагаемых правил валидации помечены `xfail(strict=True, raises=AssertionError)` с описанием причины. Неожиданное прохождение делает прогон красным; сетевые ошибки не маскируются как ожидаемый провал.
- Автозапуск тестов в GitHub Actions.


## Структура
```
├── api/
│ ├── client.py # клиент Restful-booker
│ └── schemas.py # pydantic-модели ответов
├── tests/
│ ├── config.py # адрес сервера и логин/пароль
│ ├── data.py # тестовые данные
│ ├── conftest.py # фикстуры
│ ├── test_auth.py
│ ├── test_create_booking.py
│ ├── test_get_booking.py
│ ├── test_update_booking.py
│ └── test_delete_booking.py
├── pytest.ini
├── requirements.txt
└── README.md
```

Workflow находится в корне репозитория: `../.github/workflows/tests.yml`.
GitHub Actions запускает тесты из папки `api-tests-restful-booker` при push в `main`, при pull request и вручную через `workflow_dispatch`.

## Запуск
```bash
git clone https://github.com/linuwuu/qa-portfolio.git
cd qa-portfolio/api-tests-restful-booker
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pytest
```

## Полезные команды
```bash
pytest -m smoke        # только основные проверки
pytest -m negative     # только негативные
pytest -v              # подробный вывод
```

## Особенности тестируемого API

Коды `400` в таблице — предполагаемые требования к валидации для учебных негативных сценариев, а не подтверждённый контракт API. Эти расхождения не заявляются как доказанные нарушения спецификации. Фактическое поведение ниже описывает наблюдения, на которых основаны тесты.

| Сценарий | Основание проверки | Наблюдаемое поведение |
| :--- | :--- | :--- |
| Неверные логин/пароль | Проверка текущего поведения: `200`, причина ошибки и отсутствие токена | `200` и `{"reason": "Bad credentials"}` |
| Бронь с неверными типами данных | Предположение: `400` | Не отклоняется с `400`; сценарии помечены `xfail` |
| Бронь с невалидными значениями | Предположение: `400` | Не отклоняется с `400`; сценарии помечены `xfail` |
| Бронь без обязательного поля | Предположение: `400` | `500`; сценарии помечены `xfail` |
| Успешное удаление | Документированный ответ `201` | Тест проверяет `201` и последующий GET с `404` |
