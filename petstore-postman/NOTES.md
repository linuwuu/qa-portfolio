# Petstore — Pet API tests

Коллекция для ресурса Pet в Swagger Petstore v2. Здесь 11 позитивных проверок, 9 негативных и один сценарий из 7 шагов. Вся логика находится в самой коллекции: отдельного генератора, проекта Node.js и дополнительных JS-файлов для её работы не нужно.

## Что импортировать

- `Petstore.postman_collection.json` — коллекция Petstore API tests.
- `Petstore.postman_environment.json` — окружение; необязательно, значения уже есть в Variables коллекции.
- `fixtures/pixel.png` — файл для запроса Upload a pet photo, импортировать как коллекцию не нужно. Выбрать его в Body → form-data → file, если Postman не нашёл относительный путь.

Это новая версия. Чтобы не путаться, старую импортированную коллекцию можно переименовать или убрать после проверки новой.

## Почему три папки

| Папка | Смысл | Как запускать |
|---|---|---|
| Positive tests | Валидные данные и работающие операции | Любой запрос отдельно через Send |
| Negative tests | Некорректные данные или отсутствующая запись | Любой запрос отдельно через Send |
| E2E → Pet life cycle | Создать → получить → изменить → проверить → найти → удалить → проверить удаление | Папку целиком в Collection Runner, начиная с шага 1 |

Первые две папки не зависят от порядка запуска. Последняя намеренно использует одного питомца между шагами. Pet life cycle — последовательный API workflow. Сам по себе CRUD не подтверждает полный E2E-процесс магазина. E2E не требует обязательного UI, но требует определённого процесса от начала до результата и проверку участвующих в нём частей системы. Здесь покупка и оплата не проверяются.

Проверки пустых значений не выделены в отдельную папку. Swagger не запрещает пустые name/photoUrls, поэтому нет основания автоматически ожидать ошибку. В Create a pet without tags and status пропущены необязательные tags и status. Обязательное photoUrls присутствует как пустой массив; name тоже присутствует. ID и category оставлены для управления тестовыми данными. В негативных запросах without the name field и without the photoUrls field соответствующее поле полностью отсутствует.

## С чего начать разбор

Открой Positive tests → Get a pet by ID.

1. В Pre-request генерируются ID и данные. GET подтверждает, что ID свободен, затем POST создаёт питомца.
2. Основной запрос получает этого питомца по ID.
3. Общие проверки коллекции проверяют статус, Content-Type и схему.
4. В Post-response запроса данные сравниваются с созданными. В конце питомец удаляется, а повторный GET подтверждает 404.

Начать можно с этих четырёх шагов, не разбирая всю коллекцию сразу.

## Где находятся общие проверки

Нажать название коллекции → Scripts, а не отдельного запроса.

В Pre-request коллекции задаются обычные ожидания: HTTP 200 и выключенная проверка Pet schema. Скрипт конкретного запроса меняет их при необходимости. Например, негативный GET устанавливает ожидаемый 404, а позитивный GET включает проверку Pet schema.

В Post-response коллекции находятся одинаковые для запросов проверки. Postman выполняет родительские scripts вместе со scripts запроса: сначала collection-level, затем request-level. Поэтому проверки видны в Test Results, даже если их нет в редакторе отдельного запроса.

Cleanup находится в запросе, а не в общем Post-response: иначе питомец мог бы удалиться раньше проверочного GET самого запроса.

## Какие переменные используются

| Переменная | Для чего | Где хранится |
|---|---|---|
| `baseUrl` | Адрес API с `/v2` | Variables коллекции или environment |
| `apiKey` | Публичный демо-ключ `special-key` из Swagger | Там же; это не секрет |
| `petSchema` | Непустая JSON Schema для ответа Pet | Variables коллекции |
| `petId`, `petName`, `owner` | Данные текущего независимого теста | Локальные `pm.variables` |
| `pet` | Исходные данные fixture в виде JSON-строки | Локальные `pm.variables` |
| `expectedStatus`, `checkPetSchema` | Настройки общих проверок текущего запроса | Локальные `pm.variables` |
| `flowPet`, `flowName` | Состояние последовательного сценария | Локальные `pm.variables` в рамках Runner |

Локальные переменные не сохраняют тестовые ID в экспортированное окружение. Независимый запрос заново создаёт свои значения. В life cycle состояние сохраняется между шагами одного запуска; следующий полный запуск начинает его заново.

## Почему такой ID и owner

Сервер может сам выдавать int64, который JavaScript округляет. Здесь ID строится из части случайного GUID и остаётся меньше `Number.MAX_SAFE_INTEGER`. Это даёт точное числовое сравнение без regex для извлечения ID из ответа.

Перед созданием проверяется, что ID свободен. Абсолютной защиты от одновременной записи другим пользователем публичного стенда нет: проверка и POST не атомарны.

`owner` записывается в `category.name`. Перед cleanup проверяются и ID, и этот маркер. Если маркер не совпал, тест падает и чужая запись не удаляется. Это техническая метка тестовых данных, а не новое поле контракта.

## Зачем send, Promise и await

В начале scripts с дополнительными HTTP-вызовами есть небольшой блок `send`. Он выполняет две задачи:

1. Подставляет `{{baseUrl}}`, `{{petId}}` и другие переменные во вспомогательный запрос.
2. Превращает callback у `pm.sendRequest` в Promise, чтобы можно было написать `await send(...)` и дождаться ответа перед следующим действием.

`JSON.stringify(request)` превращает описание запроса в строку, `pm.variables.replaceIn(...)` подставляет переменные, а `JSON.parse(...)` возвращает объект. В body таких дополнительных запросов уже используются сформированные тестовые данные.

Async-функция вокруг script нужна для совместимости с Newman, где top-level await поддерживается не во всех версиях. `.catch(...)` превращает непредвиденную ошибку script в failed test. В Pre-request он также отменяет основное действие, если подготовка не завершилась.

Это обычный вспомогательный блок внутри экспортированной коллекции. Внешних библиотек, eval и сетевой загрузки JS нет.

## Зачем try / finally

В Post-response позитивного запроса проверки расположены в `try`, а cleanup — в `finally`. Даже если чтение ответа или проверочный HTTP-вызов выбросит исключение, очистка всё равно будет предпринята. Обычные failed assertions внутри `pm.test` Postman и так перехватывает и записывает в Test Results.

Если запрос DELETE уже удалил питомца, cleanup увидит 404 и повторно удалять его не будет.

Это не гарантия очистки при закрытии приложения, остановке Runner или потере сети. Ошибка до входа в Post-response тоже может оставить ресурс. Здесь нет фонового процесса восстановления; при неуспешном setup или cleanup нужно посмотреть Console и проверить созданный ID вручную.

## Что именно сравнивается

Для POST/PUT ожидаемые значения берутся из реально отправляемого Body после подстановки переменных. В GET — из fixture, созданной самим тестом. После обновления выполняется отдельный GET: успешный ответ PUT не доказывает сохранение изменений.

`deep.include(expected)` проверяет все переданные ожидаемые поля, включая вложенные значения. Он допускает дополнительные поля верхнего уровня, которые сервер вправе вернуть. Это не полный deep equal всего ответа.

Pet schema взята из `definitions.Pet` официального Swagger; ссылки на Category/Tag раскрыты. `name` и `photoUrls` обязательны. Неизвестные поля не запрещены контрактом — `additionalProperties: false` не добавлялось. Swagger-формат `int64` убран как неподдерживаемая JSON Schema-аннотация, но тип `integer` сохранён.

Для поиска проверяется наличие собственного питомца. Один `forEach` по результатам недостаточен: на пустом массиве он прошёл бы без проверки хотя бы одного элемента.

## Откуда взяты ожидания

Источник: [Swagger Petstore v2](https://petstore.swagger.io/v2/swagger.json), версия 1.0.7, проверен 11 ноября 2026 года.

У POST/PUT/DELETE Pet в Swagger не описан успешный 200 response. Здесь 200 — наблюдаемая baseline стенда. Для GET, поиска и upload успешные ответы описаны в Swagger.

Негативные ожидания опираются на описанные response-коды, required-поля и enum. Общий POST `405 Invalid input` применяется к нарушениям схемы; подробное соответствие validation errors кодам контракт не уточняет. Для реального продукта это повод задать вопрос владельцу API.

### Известные расхождения публичного сервера

| Запрос | Ожидается по контракту | Наблюдалось |
|---|---|---|
| Get/Delete с нечисловым ID | 400 | 404 |
| Find с неизвестным status | 400 | 200 |
| Update отсутствующего питомца | 404 | 200 и создание записи |
| Create без name/photoUrls | 405 Invalid input | 200 |
| Create с неизвестным status | 405 Invalid input | 200 |

Такие тесты остаются failed. Cleanup удаляет неожиданно принятые данные. Пустое значение поля и отсутствие обязательного поля — разные условия; ожидания для них не смешиваются.

## Границы проекта

Scope: Pet JSON API — CRUD, фильтр по каждому статусу, form update, upload PNG и последовательный life cycle. Не покрыты Store/User, deprecated findByTags, XML, OAuth, полный диапазон int64, конкурентные операции, нагрузка и все варианты файлов. Проверка upload не доказывает сохранение изображения: контракт не предоставляет endpoint для его скачивания.

## Результаты проверки

Проверено 11 ноября 2026 года через Newman 6.2.1 на публичном `petstore.swagger.io/v2`:

- Официальная схема формата Postman Collection v2.1 и синтаксис scripts — PASS.
- Все 11 позитивных запросов и 7 шагов Pet life cycle — PASS.
- Из 9 негативных запросов: 2 PASS и 7 FAIL по причинам из таблицы выше.
- Полный прогон: 104 HTTP-запроса вместе с setup/cleanup; 159 из 166 assertions прошли. Сетевых ошибок и ошибок scripts нет.
- Все 20 независимых запросов повторены по одному в новых runtime, в обратном порядке внутри папок. Воспроизвелись те же 7 расхождений, без новых ошибок; очистка проверена.

Негативные проверки с расхождениями дают ненулевой exit code. Коллекция проверена официальной JSON Schema и запуском Newman; ручной импорт в интерфейс Postman при этой проверке не выполнялся.

Для необязательного CLI-запуска из этой папки, если установлен Node.js:

```sh
npx newman@6.2.1 run Petstore.postman_collection.json --folder "Positive tests" --working-dir .
npx newman@6.2.1 run Petstore.postman_collection.json --folder "Pet life cycle" --working-dir .
```

В CLI путь `fixtures/pixel.png` должен разрешаться от корня проекта. Основной способ работы с коллекцией — Postman; отдельная CLI-инфраструктура в проект не добавлена.
